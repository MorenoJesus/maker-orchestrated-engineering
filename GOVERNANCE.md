# Project governance

**Proposed governance | working draft**

The repository owner is the initial decision authority. This document does not appoint additional maintainers, create an organization, or claim external endorsement.

## Changes

Editorial corrections may use ordinary pull requests. Changes to core semantics, contract fields, conformance rules, autonomy boundaries, licensing, or claim language should use the RFC process. Each substantive change should state motivation, alternatives, compatibility, security effects, examples, and migration impact.

Review normative requirements and examples together. A schema change must include positive and negative tests. A claim of tool support must include a verified version and source or be labeled unverified. No provider may become a core requirement merely because a reference implementation uses it.

## Versioning

The foundation is version 0.3.0, continuing the working-draft discussion. No public 0.1 or 0.2 release is implied. Before 1.0, minor versions may change semantics or schemas; migration notes are still required. Patch versions should not intentionally break record compatibility. Version the specification, schemas, profiles, and examples explicitly.

Do not silently edit a published evidence artifact or historical decision. Corrections should preserve prior records and explain what changed.

## Decision principles

Prefer implementable requirements, clear uncertainty, small records, and evidence of usefulness. Preserve lifecycle and vendor neutrality. Do not claim novelty, benefits, compliance, or conformance beyond the evidence available.
